# SinchPushSocket — port of the React Native core

The foreground WebSocket "push relay" client. The relay channel is alive only while the app is in the foreground; background/killed → APNs. Everything in this folder is `internal`; the public surface lives on `SinchPush` and is wired in `Sources/SinchPushSDK/Relay/PushRelay/` (see "SDK integration"). Type, function and file names are the RN ones, so a diff against the RN tree stays readable.

**Message order (SB-62 / SB-65)** — per message, on a dedupe miss, in this order (RN `emitMessage`): registry insert (persisted) → `last_seen` cursor persisted → DELIVERED queued **and flushed** → pending store → `onMessage` → display rule → **lookup** `isDelivered(message_id)` → post, or, when the notification is already in the notification centre, `markShown` and nothing else (no DISPLAYED, no alert slot, a log line). So the event is emitted for such a message — the lookup decides the banner only. The answer arrives on the system's queue and is hopped onto the scheduler; it is dropped when the client was stopped or reconfigured meanwhile (`sessionEpoch`, `stopped`). A `suspend()` does not drop it.

**RN-044 / RN-045 rules kept as RN has them** — `takeAlertSlot` has no backwards-clock guard (a clock stepped back silences alerts until it catches up); `threadIdentifier` = the trigger's, else `"sinchpush"` (SB-63); `SeenMessageRegistry` API is `markSeen(_:) -> Bool` / `contains` / `snapshot` with a lazy first-use load, state behind an unfair lock; `sessionEpoch` is bumped by `stop()`, a terminal stop and `updateConfiguration` (so a relay-initiated stop such as `auth_required` / `replaced` also drops the pending post); the delivered lookup is `DeliveredNotificationLookup.isDelivered(identifier:completion:)`.

It is checked at the existing trigger points (`sendTokenIfNeeded`: token arrival, and `pushRepository` assignment after `setIdentity`) and recorded with exactly the info that was sent. The old `sinch_sent_token_dictionary` is still written but no longer read: a record with no fingerprint (an older SDK's) counts as changed, so the first launch after the upgrade re-subscribes once; a corrupt fingerprint blob reads as empty.
- **`removeIdentity`** (RN-043 parity): after a **successful** unsubscribe the handler clears the sent-token record and the subscription fingerprint for that identity (`PushDeviceTokenCoordinator.clearSentRecord(for:)`, hash read before the auth token is deleted), so a re-login with the same identity subscribes again. A failed unsubscribe keeps both (the subscription may still exist). The device token is kept. The short-lived handler it builds to unsubscribe does not subscribe when its repository is assigned (`subscribesOnRepositoryChange: false`), since a changed fingerprint would otherwise race a Subscribe against the Unsubscribe.

## Swift 6 concurrency approach

The package is `swiftLanguageModes: [.v6]` (complete checking). The RN design is kept: **all client state is serialised on one `Scheduler`** — a serial `DispatchQueue` in production, an inline manual scheduler in tests — and every entry point (public methods, transport callbacks, timers, presenter completion) goes through `scheduler.perform` / `schedule`.
- `SocketClient` is `final class … : @unchecked Sendable`; its doc comment states the invariant — stored state is read/written only on the scheduler.
- Host-readable state (`currentState`, `currentPendingMessages`, `setCallbacks`, `setHandlerRegistered`) keeps `callbacks` / `state` / `pendingMessages` in one `OSAllocatedUnfairLock<Shared>` behind computed properties, so the state-machine code is unchanged.
- Dependency protocols (`Scheduler`, `ScheduledTask`, `RandomSource`, `SocketTransport`, `SocketTransportFactory`, `NotificationPresenting`, `SocketStateStore`, `AuthTokenStore`, `SocketLogger`) are `AnyObject, Sendable`; every cross-thread closure (`perform`/`schedule`, transport `onOpen`/`onBinary`/`onClose`, the `post` completion, `SocketClient.Callbacks`, logger sink, presenter hooks) is `@Sendable` and captures `self` strongly *after* a `guard let self` (a `[weak self]` inside a nested `@Sendable` closure is a captured `var`).
- `URLSessionWebSocketTransport` (session, task, flags, callbacks), `NoopNotificationPresenter.handlerRegistered` and the `SocketNotificationPresenter` registration flag are lock-protected; no callback and no `URLSession` call is made while the lock is held. `UserDefaultsSocketStateStore`, `InMemorySocketStateStore`, `InMemoryAuthTokenStore`, `DispatchScheduledTask` and the non-Security `SocketAuthTokenStore` fallback are `@unchecked Sendable`, each with its invariant (client-confined, or `DispatchWorkItem.cancel` is thread-safe).
- `UIApplicationSocketLifecycle` and `AppLifecycleObserving` are `@MainActor` (observers on `queue: .main` + `MainActor.assumeIsolated`, `isolated deinit` removes them). The presenter is deliberately **not** `@MainActor`: the client calls `post` from the scheduler and a main-actor hop would change the sequencing DISPLAYED relies on.
- Test fakes are `@unchecked Sendable` and unsynchronised on purpose (driven by the inline test scheduler on one thread); test state touched from real threads (`Live` / `Box` in `LiveRelayContractTests`, `Recorder` in `LiveRelaySmokeTests`, the presenter in `BackgroundPresenterCompletionTests`) is guarded by `NSLock`; the three `nonisolated(unsafe)` statics in `LiveRelayContractTests` (class `setUp`/`tearDown` state, XCTest runs serially) are the only `nonisolated(unsafe)` uses. `@preconcurrency` is not used anywhere. Transport delegate callbacks arrive on `URLSession`'s queue and reach the state machine only through the client's `scheduler.perform` closures, as in RN.
- `backoffState` and `resolvedPollIntervalMs(serverMs:)` are test hooks that read confined state and must only be called from the scheduler's context (the inline test scheduler).

## SDK-only additions to the shared core (prerequisites for the plan §5c shared package)

The core is RN's except for the items below. Each exists because the SDK's lifecycle (identity changes, a process that outlives sessions, APNs and socket in one process) needs it; the shared package has to carry them or the extraction loses behaviour.
- **`SocketClient.retire()`** — `stop()` plus `retired = true`, a `generation` bump and `retired` guards in `handleOpen` / `handleBinary` / `handleTransportClose` / `storePending` / `advanceLastSeen`. *Why:* every client of the process shares one store, so a replaced client must stop writing to it — a late presenter completion would otherwise queue DISPLAYED on the old tracker and write the old identity's whole outbox back over the new one. A retired client turns `start`, `updateConfiguration`, `report`, `resetSessionState`, `reloadSessionState`, `clearPendingMessages` and the `post` completion into no-ops, and in-flight transport callbacks are ignored (the generation bump). Callers do any store clean-up **before** `retire()`.
- **`removeIdentity` / retire contract.** `removeIdentity` (`PushSocketManager.stop()`) stops the relay (in-memory token and relay-configuration copy cleared on the client's scheduler, after `stop()`), clears the pending-message store, outbox and cursor but **keeps the seen set** (ids are unique across identities), and replaces the client with a fresh idle one that runs `resetSessionState()` — so a DISPLAYED that completes after the removal is not queued for the next user.
- **`resetSessionState()` / `reloadSessionState()`**, run on the core's scheduler. *Why:* the outbox clean-up must go through the core, not from the manager: a client built next to the previous one reads the outbox in `ReportTracker.init` on the main thread, before the previous client's last queued writes may have run.
- **`ReportTracker.clearOutbox` / `reloadFromStore` / `retire`** — the tracker-side halves of the above (`retire()` empties memory and makes `persistOutbox()` / `persistSentKeys()` (RN-055) and `reloadFromStore()` no-ops). *Why:* a retired tracker must not re-persist an outbox nobody may see.
- **Session owner** — the outbox and `last_seen` belong to an `appID|projectID|userID` (`RelaySessionOwnerStoring` in UserDefaults + a main-actor mirror). *Why:* the core keeps one outbox and one cursor with no notion of a user; a different owner (or none recorded) clears both, the same owner (cold launch, retry from a terminal state) keeps them, `removeIdentity` clears both and sets the owner to `nil`, and `reportStatus` with no owner is dropped and logged. The owner is persisted on the scheduler after the clean-up.
- **Required `seenRegistry:` injection** on `SocketClient.init` (RN defaults to a private `SeenMessageRegistry`). *Why:* a private registry over the shared store would dedupe against itself only and race the real one on the persisted list. RN's one test of that default (`aClientBuiltWithoutARegistryStillDedupesOverItsOwnStore`) is not ported.
- **`PushPresentationDecider` `apnsMarked` difference.** RN shows an APNs push from `willPresent` and only emits its JS event from `didReceiveRemoteNotification`, so its decider leaves a foreground alert push *unmarked* in the second and lets `willPresent` mark it. This SDK shows in-app content from `handleNotification` (the host's `didReceiveRemoteNotification`) **and** decides the banner in `willPresent`, and iOS gives no order between them for a foreground content-available push. *Why:* "mark in the first, suppress in the second" would hide a message nothing had shown, while a `handleNotification` that never dedupes shows a socket message a second time. The rule (plan §5b.5) is to suppress only what was **already seen over another channel**: `decide` → no id ⇒ present; else `isCopyFromOtherChannel(id)` — new ⇒ remember the id in the bounded in-memory `apnsMarked` set (ids first marked by the APNs path in this process) and present; already in the registry ⇒ a copy unless `apnsMarked` holds it. So the same push's `willPresent` and `handleNotification` never suppress each other in either order, while the socket's copy (and an id from an earlier process, which only the registry remembers) is suppressed. Cost: a second APNs delivery of one id in one process is presented again (APNs collapses on `apns-collapse-id`).
- **Presenter completion hops onto the scheduler** (`SocketClient.emitMessage`). *Why:* in RN the `post` completion ran where the presenter completed it (for the live presenter, a `UNUserNotificationCenter` queue) and then touched `pendingMessages`, the tracker and the transport from that queue. With `DispatchScheduler` DISPLAYED is queued one scheduler turn later (`BackgroundPresenterCompletionTests` pins it: DISPLAYED queued exactly once and `shown` persisted when the completion arrives from a background queue); with the inline test scheduler it is identical, because every test presenter completes synchronously.
- **`makeRequest(for:alerting:)` split out of `post`.** *Why:* the notification content (sound / passive / thread / identifier) must be testable without a `UNUserNotificationCenter`.
- **`SeenSet.init(persisted:)` keeps the newest ids** when handed more than the capacity (RN takes `prefix`, i.e. the oldest). *Why:* a restart must not drop the ids of the most recent messages. Unreachable today (the bound was never above 2000); flagged to RN.
- **Always ack `DELIVERED` on a dedupe hit** (plan §8; mirrored — RN adopted the rule in RN-049, `7489b43`). *Why:* a silent hit is a false ACK_TIMEOUT and the relay answers one with a duplicate push. `emitMessage` queues and flushes DELIVERED on a registry hit exactly as on a miss, then stops: no event, no pending entry, no notification, no DISPLAYED. SB-30 (at most once per `(message_id, status)`) keeps a redelivery from counting twice, and the cross-channel case (APNs marked the id first, so nothing was ever reported to the relay) is the one that needs it.
- **128-byte clamp for `os_version` / `bundle_id` / `sdk_version`** (CONTRACT `d0e0d80` §2.6; RN to mirror). *Why:* the relay contract caps these fields; the clamp cuts on `Character` boundaries so a grapheme cluster is never split, and a cluster wider than the cap yields nothing rather than half.
- **`BackgroundServiceState.RELAY_DISABLED` reporting + the runtime toggle** (core mirrored from RN-048 / SB-66, `95e3b7e`; the effective-state wiring is SDK-only). *Why / how:* `RELAY_DISABLED = 5` is in the pinned relay contract (`d0e0d80`, CONTRACT §2.5: a Hello carrying it with `background = true` is accepted, stored foreground-only and counted as `delivery_ws_hello_contradictions_total{reason="relay_disabled"}`), which is what the provider reports while its `RelaySwitchStore` is off. The SDK's store is `RelaySettings.effectiveSwitch`: `isEnabled` is the **effective** state (kill switch + runtime switch + region), not just the runtime switch, and it is injected into the one `SystemDeviceInfoProvider` kind used by both Subscribe and the socket (`SinchPushSDK`, `PushSocketManager.Dependencies.live`), so Subscribe reports `UNSUPPORTED` while the relay is effective and `RELAY_DISABLED` otherwise (a Hello only exists while it is effective); no configuration known (no `setIdentity` yet) counts as disabled, and a Subscribe cannot happen then anyway (no identity). The runtime toggle is `SinchPush.setRelayEnabled(_:)` (`UserDefaults` key `com.sinch.push.relay.enabled` — RN's, via `UserDefaultsRelaySwitchStore`; default on, persisted so Subscribe does not flip-flop across launches); off → `endSession()` + state `.stopped` / `relayEnabled=false` / `disabledReason "relay disabled at runtime…"`, on → a new client like a retry (token possibly expired: one `auth_required` → refresh round trip). The identity, the subscription and the session owner stay. `background_service` is already in the coordinator fingerprint, so every change of the effective state sends exactly one Subscribe at the next `sendTokenIfNeeded` (triggers: the toggle via `PushNotificationHandler.resubscribeIfNeeded()`, and a `setIdentity` with another `relay` / region, which sets `RelaySettings.appConfig` before the token request). Pending reports are **kept** on toggle-off: the outbox belongs to the identity, not the socket, is bounded, and is sent again when the relay runs (a toggle-on or the next launch); it is cleared by `removeIdentity` or a different identity. Only messages the core held for the host and had not published yet are dropped, as on every session end.
- **Toggle mechanics.** `PushSocketManager.relayEnabledDidChange()` re-runs `start` with the configuration, token and auth source the manager already holds; turning off calls `endSession()` (socket closed, lifecycle observer removed, relay configuration and token copies cleared). An identity change clears the stored relay inputs **even while the socket is off**, so a later toggle-on cannot start a replaced identity. Subscribe re-evaluates on the main actor after an in-flight call completes, so the backend converges on the latest effective state instead of losing the change.
- **`RELAY_DISABLED` plumbing.** `DevApp/proto/sinch/push/v1beta1/resources.proto` is byte-identical to relay `d0e0d80`; the generated case is `Sinch_Push_V1beta1_Resources_BackgroundServiceState.relayDisabled`. Relay disabled ⇒ no socket and no Hello at all; only Subscribe carries the value.
- **`SocketLogger.log(_:level:)`** (`SocketLogLevel`: `.verbose` / `.warning` / `.error`; `log(_:)` stays `.verbose`) — RN's core logs a single level. *Why:* production `Logger` drops verbose, so actionable failures (transport/decode/auth/Keychain errors, dropped or retried reports) must reach `Logger.warning` / `Logger.error`; the SDK adapter (`PushSocketManager.Dependencies.sdkLog`) maps the level, message texts are RN's.
- **SDK wiring injects an in-memory token store and a configuration-less state store** (`NonPersistingConfigurationStateStore` + `InMemoryAuthTokenStore`, wired in `PushSocketManager+Live.swift`). *Why:* the core's relaunch persistence (RN SB-35, core-only: `PersistenceTests.test_SB35_aRelaunchedClientResumesFromPersistedStateAndTheToken`) is unused in the SDK — the manager always passes the configuration to `start()` / `updateConfiguration()` and nothing cold-starts a socket from the store, so **no JWT and no socket configuration is persisted by the SDK**. The core is unchanged and still writes both through its seams; the SDK never hands it a store that persists them. Every other slice (seen set, reported keys, `last_seen`, outbox, pending messages — all needed across a launch) is forwarded to the shared `UserDefaultsSocketStateStore`. `clearConfiguration()` still forwards, and `+Live` clears the Keychain token and the configuration key once per process, so a copy written by an earlier build is deleted rather than left behind.

## SDK integration (`Sources/SinchPushSDK/Relay/PushRelay/`)

Host-facing docs: `Documentation/PushRelay.md`.
- **Wiring**: `PushSocketManager` (`@MainActor`, one per process via `SinchPushSDK.pushSocketManager`) owns the client, the presenter, the lifecycle observer and the Combine subjects (`stateSubject`, `messageSubject`, published on the main actor). The registry is created by `SinchPushSDK` over `UserDefaultsSocketStateStore` and shared with `SinchPush`'s APNs routing.
- **Effective relay state**: `RelaySettings` is the one place that combines them — `AppConfig.relay == .enabled` **and** the runtime toggle on **and** `RelayEndpoint.resolve` gives a usable URL (`EU1`/`US1` have none today; `ws://` needs `AppConfig.allowInsecureRelay`). The socket manager starts a socket only when it holds, and the Subscribe path asks the same object, so the two cannot disagree; transient states (not connected, backgrounded, `auth_required`/error) never change it.
- **Claims** (`RelayJWTClaims`, `SocketConfiguration.relay(url:auth:config:)`, mirroring RN `src/api/jwtClaims.ts`): `appId` / `app_id` required, `projectId` / `project_id` falling back to `config.projectID`, user id = `AuthModel.getUserID()` (`uuid`) required; missing ⇒ no start, `status = .error`, `lastError` names the claim. Display rule `.always`.
- **Config** (`Region.custom(…, relayURL:)`, RN-046): `custom` requires `relayURL`; `wss://` always, `ws://` only with `allowInsecureRelay` (≙ RN `allowInsecureWs`) — **not** `isSecure == false`, which also makes the chat gRPC channel plaintext (`Default2APIClient`). `AppConfig` decodes without `allowInsecureRelay` as `false` and without `relay` as `.enabled`; `Region` keeps its encoded shape (no `relayURL` key when `nil`) so Keychain-persisted `AuthModel`s decode. The token cache compares regions **without** `relayURL` (`Region.withoutRelayURL`), so toggling the relay URL never re-issues a token (for `.anonymous` that would create a new user).
- **Start / stop on identity**: start only from the successful completion of `setIdentity`, on the main actor, and only if no other `setIdentity` / `removeIdentity` happened since the call (`identityChangeCounter`), so a slow completion cannot start the relay for a replaced identity. A new identity — or the host retrying from a terminal state — gets a **new `SocketClient`** (the old one `retire()`d, its events ignored via the generation counter, lifecycle observer rebuilt), because the core allows one `onAuthRequired` per `start()` and `updateConfiguration` does not re-arm it; same identity + new token → `updateConfiguration`; same identity + same token → nothing. The client created in the manager's `init` is only the one that queues `reportStatus` before the first session; those reports persist in the outbox and the next client's tracker reads them. `removeIdentity` stops the relay *immediately*, before the unsubscribe RPC, and does not restart it if the RPC fails (a failed `removeIdentity` keeps the identity but not the relay until the next `setIdentity`, which hosts call at launch). `setIdentity` for another identity stops a running relay when it is *called* (`identityWillChange`); the outbox is left to the session-owner rule. If `setIdentity` completes in the background the client is suspended right after it is configured (SB-56). State from a stopped or replaced client is ignored, so a late `.stopped` cannot overwrite the "relay disabled" state published by `stop()`.
- **`auth_required`**: `onAuthRequired` (once per client) → `AuthDataSource.refreshToken()` (`DefaultAuthDataSource` re-issues with the stored signed identity via the repository, bypassing the cache, and saves unless the identity changed meanwhile) → `SocketConfiguration.relay(...)` from the new token → must be the same session (user / app / project / url) → `client.updateConfiguration`. Any failure publishes `status = .error` with `lastError` and logs; a refresh that finishes after `stop()` / an identity change is discarded (`sessionID`). **Anonymous identities are not refreshed** — `createAnonymouseToken` mints a *new* anonymous user and would orphan the current one's conversations — so the relay stays off for them (`.error`, `lastError` `anonymousTokenCannotBeRefreshed`) until the next `setIdentity`; flagged as an open question.
- **In-app routing**: `InAppRoutingNotificationPresenter` wraps the real presenter. The core calls `onMessage` first and `post` after; `post` is offered to `DefaultInAppMessageController` on the main queue and, when it shows the message (owner `sinch` + decodable `protobufPayload`), completes `true` without a system notification — DISPLAYED is still reported, which is accurate (it was shown). The alert slot of RN-044 is claimed before `post`, so an in-app message uses up the window; harmless. The presenter has **no** response handling — the SDK handles the response in `DefaultSinchPush` (testable without a `UNNotificationResponse`), so there is one path.
- **Dedupe entry points** (`DefaultSinchPush`, `PushMessageRouting`): dedupe applies to **Sinch pushes only** — `PushMessageIdentity.messageId` (key `PushMessageIdentity.metadataKey = "sinch.push.message_id"`) returns an id for a payload with `sinch.push.message_id` or, for a payload with another `sinch.push.*` key, a non-UUID request identifier; no id ⇒ no dedupe, since a host's own notification identifiers are the host's.
  | Entry point | Behaviour |
  |---|---|
  | `handleWillPresentNotification` (APNs) | `decide` ⇒ `.suppress` ⇒ `[]` (handled, addressees not consulted); otherwise today's behaviour via the addressees. |
  | `handleWillPresentNotification` (socket-sourced) | recognised by `userInfo["source"] == "socket"` **and** the socket category `sinchpush.socket` (when the category is known: a remote payload can carry any `userInfo`). Never deduped (the socket put the id in the registry itself). Goes through the addressees like an APNs push (so the open-conversation rule applies); a notification without sound (a non-alerting post of RN-044) is then never given more than `[.list, .badge]` (the deprecated `.alert` counts as banner + list), whoever claimed it; if none claims it: `[.banner, .list, .sound]`, or `[.list]` without sound. Never `nil`. |
  | `handleNotification(_ payload:)` | `decide(payload, requestIdentifier: nil)` ⇒ `.suppress` ⇒ `true` without in-app / addressees; otherwise in-app / chat as before. |
  | `handleNotificationResponse` | socket + `UNNotificationDismissActionIdentifier` ⇒ `reportStatus(.dismissed)` (queued), returns `true`, opens nothing. Everything else (incl. a tap on either channel) ⇒ for an APNs notification `decide` marks the id seen (result ignored: a tap is never suppressed) and `handleNotification(payload:)` runs as before. |

## Known deviations and open items

**Behavioural deviations: none intended.** The state machine, the report tracker, the codec, the backoff and all SB-xx rules are the RN source; the Swift 6 changes above are about *how* state is protected, not what the client does. Only two change *when* something runs in production: **deviation 1** the presenter-completion hop onto the scheduler (see "SDK-only additions"), **deviation 2** the removal of a dead write (the closure's `event.shown = true` on a captured `var` copy that nothing read — the persisted flag is set by `markShown`; Swift 6 rejects mutating a captured `var` in a `@Sendable` closure).
- RN behaviours deliberately **kept, not fixed**: `URLSessionWebSocketTransport.close(code:reason:)` consumes its `closingLocally` flag in `teardown`, so the cancelled `receive` fails on `URLSession`'s queue, calls `reportClose` and — if a handler is still installed — delivers `onClose(1006)`; the client never hits this because `closeSocket()` clears the handlers *before* `close`, which is what SB-51 relies on (`URLSessionWebSocketTransportTests` pins that ordering). The RN `OperationQueue` that `connect(to:)` created and the `SocketState` / `SocketMessageEvent` `dictionary` bridge shapes are not ported (no JS bridge here).
- **Open items for RN** (things RN should mirror or decide): `SeenSet(persisted:)` should keep the newest ids, not the oldest. Clamp `os_version` / `bundle_id` / `sdk_version` to 128 UTF-8 bytes on `Character` boundaries (CONTRACT `d0e0d80` §2.6); RN does not clamp yet. `SocketClient` should require an injected `seenRegistry:` instead of defaulting to a private one over the shared store, which would also change RN's own default-registry test. RN-048 (`95e3b7e`, SB-66), RN-049 (`7489b43`, always-ack) and RN-052 (`825ecf4`, 48 golden vectors) are mirrored here; RN-053 (`4ce94b4`, sent-set cap) and RN-055 (`8e6dd42`, sent-set written only when it changes) are mirrored; RN-054 (`8ed8cff`) is **not applicable** (RN's live-contract harness, per-installation replay + isolation: no core change, and this repo's `LiveRelayContractTests` is macOS-only and not compiled here), so **thirteen of fourteen `swift:` commits** are mirrored; RN-050 / RN-051 (`cb65866`, audit follow-ups) have no Swift commit to mirror. RN-051 repinned sinch-push `sdk.proto` to sinch-push `9374663`; this SDK's `DevApp/proto/sinch/push/sdk/v1beta1/sdk.proto` follows the relay CONTRACT §2.4 snippet, and `9374663` additionally changes Subscribe's response to `SubscribeResponse` (wire-compatible; the SDK ignores the response) — **decided: no repin**, this SDK stays on the relay CONTRACT §2.4 `sdk.proto` (see `RELAY_CONTRACT_PIN.md`). Reported keys were persisted unordered before `4ce94b4`, so on the first load after an upgrade the eviction order is arbitrary (only matters above 8000 keys; same in RN). RN-052 repinned RN to `d0e0d80` as this SDK is. Anonymous identities cannot be refreshed, so the relay stays off for them — RN should decide whether that is right there too. Relay hosts for `EU1` / `US1` are derived from the region (`wss://relay.sinch-push.prod.sinch.com/ws` and `wss://relay.sinch-push.us1.prod.sinch.com/ws`, mirroring the push hosts of the environments) — RN should derive them the same way. The production relay hosts have to exist in DNS before the socket can connect to them. The facade / bridge surface is not ported on purpose: `SinchPushSocketFacade`, `*.mm`, `DeviceInfo.dictionary` and `SocketConfiguration(configMap:)`.
- **Replay UX: decided (2026-10-20)** — RN-044's behaviour stands as the conservative choice: a replay drops nothing (every message the relay sends is delivered and shown), and the alert window decides only *which* notification alerts — one alerting notification per 2 s window (`SocketClient.notificationAlertWindowMs = 2000`), the rest posted without banner or sound. Nothing is coalesced away.
